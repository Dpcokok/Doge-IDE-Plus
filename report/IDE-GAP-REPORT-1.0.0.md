# Doge IDE+ 距离完整 IDE 的差距检查报告

检查版本：1.0.0 首个测试发布版  
检查日期：2026-09-27  
检查对象：`local-runtime` 分支、Android 本地运行链路、共享 Web 编辑器

## 结论

当前项目已经是一个可用的 **单文件 C/C++ 在线式代码编辑与本地运行工具**，但还不是完整意义上的工程型 IDE。

核心编译运行链路已经成立：C17、C++20、标准输入输出、编译错误、非零退出码和超时均已在 Android 16 ARM64 平板上验证通过。当前最大差距不在“能否运行代码”，而在“能否管理真实工程、理解工程结构、调试和持续开发”。

综合判断：

- 单文件编程工具：可用；
- 教学和算法练习工具：接近首个可用版本；
- 工程型 IDE：尚未达到；
- 发布成熟度：测试发布版，尚不适合直接作为正式商店版本。

## 已具备能力

### 编辑体验

- CodeMirror 编辑器；
- C 和 C++ 语言切换；
- C17、C++20 预设；
- 语法高亮、括号匹配、自动补全；
- 当前行高亮、编辑器字号设置；
- 标准输入区域；
- stdout、stderr、info 输出面板；
- 平板触摸布局和软键盘适配；
- 本地保存代码、语言和部分编辑设置。

### 构建与运行

- 首次导入 ARM64 C/C++ 工具链资源包；
- Clang 编译；
- wasm-ld 链接 WASI；
- C++ libc++、libc++abi 和 compiler-rt 支持；
- WAMR 本地执行；
- 标准输入、输出和错误输出；
- 退出码和超时结果；
- 编译错误回传到界面；
- 资源包导入时的 manifest 校验和 ZIP 路径穿越检查。

### Android 集成

- 独立包名 `com.doge.ide.plus`；
- ARM64 native runtime；
- 应用私有目录存放工具链；
- Android 文件选择器导入资源包；
- 本地 HTTP 服务连接 WebView 和执行器；
- 已在 Android 16 平板完成核心验收。

## 关键缺口

### P0：工程模型和文件系统工作区

当前 UI 只有语言标签和一个编辑器，没有项目、目录或文件模型。代码保存在 localStorage，无法作为真实工程文件管理。

缺少：

- 新建、打开、关闭和保存项目；
- Android Storage Access Framework 工作区授权；
- 文件树和目录操作；
- 多文件标签页；
- C/C++ 头文件与源文件关联；
- 工程重命名、复制、删除和最近项目；
- 未保存变更提示；
- 项目级持久化和崩溃恢复。

影响：无法开发稍大于单文件示例的程序，也无法进行正常的工程迭代。

建议：先建立 `Project`、`Workspace`、`Document` 和 `BuildProfile` 数据模型，再接入文件树和多标签编辑器。

### P0：工程构建系统

当前编译器固定接收一段源码，并由 `LocalCompiler` 固定生成临时对象和 WASM。它不是工程构建系统。

缺少：

- 多源文件编译；
- 增量编译；
- 工程级编译参数；
- Debug/Release 配置；
- include 路径、宏定义和链接库配置；
- CMake、Make 或其他项目描述文件支持；
- 构建日志和失败阶段定位；
- 构建缓存清理。

建议：先实现 Doge 自有轻量工程格式和多文件构建，再考虑 CMake 兼容层。直接把单文件接口扩展成大量参数会使执行器继续承担工程管理职责。

### P1：真实调试器

前端保留了断点和 Debug 相关代码结构，但 Android 本地版本隐藏了 Debug 入口；当前验证的是运行和超时，不是真实调试。

缺少：

- DWARF 调试信息；
- LLDB 或等价调试后端；
- 断点设置、命中和条件断点；
- 单步、继续、暂停和终止；
- 调用栈、局部变量、监视表达式；
- 调试时源代码行映射；
- 调试进程生命周期管理。

建议：在多文件构建稳定后，把编译产物和调试会话抽象出来，再评估 Android 上 LLDB 的集成成本。当前 WASM/WAMR 执行路径不能直接提供完整 C/C++ 调试体验。

### P1：诊断和代码智能

现有补全主要是静态词表，不具备编译器语义理解。

缺少：

- 基于 clangd 的补全、跳转和符号索引；
- 查找定义、查找引用和重命名；
- 实时诊断；
- include 和宏展开诊断；
- 编译错误点击跳转到文件和行列；
- 格式化、代码操作和安全重构；
- 项目级索引缓存。

建议：优先实现诊断行列解析和错误点击跳转，然后再引入 clangd 或受限的 clang 工具服务。

### P1：终端和进程控制

当前只有一次 Run 请求对应的 stdin/stdout/stderr 面板，没有交互式终端。

缺少：

- 持久化终端会话；
- 运行中输入；
- 进程暂停、继续和强制终止；
- 环境变量和工作目录配置；
- 信号处理；
- 多个任务并行运行；
- 长输出限流和日志导出。

建议：先把编译任务和运行任务建模成可取消的 Job，再设计终端会话。

### P1：资源包和依赖管理

当前资源包为一次性 ZIP 导入，能校验基础 manifest，但没有版本管理和依赖生态。

缺少：

- 资源包版本迁移；
- 工具链升级、回滚和卸载；
- 多 ABI 资源包；
- 第三方库安装与锁定；
- 依赖缓存和离线索引；
- 资源包签名或可信来源校验；
- 存储空间检查和导入进度恢复。

### P2：用户体验和产品基础设施

缺少：

- 完整的快捷键命令系统；
- 设置分组和配置导入导出；
- 主题、编辑器布局和面板布局持久化；
- 项目模板；
- 示例工程；
- 输出复制、导出和清空之外的日志操作；
- 无障碍语义和 TalkBack 检查；
- 国际化资源管理；
- 崩溃日志和诊断信息导出。

### P2：版本控制和协作

完整 IDE 通常需要基础 Git 工作流。当前没有：

- Git 仓库初始化和状态查看；
- diff、暂存、提交和分支操作；
- 冲突查看与解决；
- 远程仓库同步；
- 项目导入导出。

Android 平板上可以先实现本地 Git 状态和 diff 查看，再决定是否加入完整 Git 命令执行能力。

## 工程质量和发布风险

### 当前风险

1. 1.0.0 目录中的 APK 是 debug 签名测试包，不能视为正式商店发布包。
2. Android `targetSdk` 为 28，这是为了允许从应用私有目录执行导入的工具链，带来平台兼容和发布策略风险。
3. 当前版本依赖单一 ARM64 ABI，不支持 x86_64、armeabi-v7a 等设备。
4. `java.nio.file.Files` 在最低 API 24 的真实运行时兼容性需要持续验证；当前构建通过不等于所有 API 行为都已覆盖。
5. 运行器的超时、并发执行、重复运行和资源清理需要更多压力测试。
6. 当前没有自动化 Android 集成测试和稳定的回归样例集。
7. 工具链约 232 MB，导入失败恢复、空间不足和中断恢复尚未形成完整用户流程。

### 已确认的验证结果

- C17 stdout：通过；
- C++20 STL：通过；
- 编译错误：通过；
- 非零退出码：通过；
- 超时：通过；
- `git diff --check`：通过；
- APK 和资源包已生成 SHA-256 校验值。

## 推荐路线

### 阶段 1：从单文件工具升级为项目编辑器

1. 项目/工作区数据模型；
2. SAF 文件授权和文件树；
3. 多标签编辑器和真实文件保存；
4. 未保存状态、恢复和最近项目；
5. 多文件 C/C++ 编译。

阶段完成标准：可以创建一个包含 `main.cpp`、头文件和多个源文件的本地项目，关闭应用后重新打开并成功构建运行。

### 阶段 2：可用的 C/C++ 工程工具

1. Build Profile；
2. include、宏和库配置；
3. 编译错误点击跳转；
4. 格式化和基础诊断；
5. 可取消任务、终端和日志导出；
6. 工具链版本管理。

阶段完成标准：用户可以反复修改工程、增量构建、定位错误并控制运行任务。

### 阶段 3：调试和开发工作流

1. 调试信息生成；
2. 调试后端选型与集成；
3. 断点、单步、调用栈和变量查看；
4. Git 基础工作流；
5. 项目模板、导入导出和设备适配。

阶段完成标准：能够在平板上完成一个中小型 C/C++ 工程的编辑、构建、调试和版本管理闭环。

## 1.1 阶段进展

截至 2026-09-27，已在 `local-runtime` 分支实现第一版内存/本地存储工作区：

- 文件列表和多文件编辑标签；
- C/C++ 源文件与头文件创建、切换、删除；
- 项目文件内容通过 WebView `localStorage` 持久化；
- Run 请求发送 `files` 和 `entry`；
- Android 编译器把项目文件写入工作目录；
- 逐文件编译 C/C++ 源文件；
- 统一链接多个对象文件；
- 保留旧版单文件 `code` 请求兼容性。

这使项目从“单文件执行器”进入“多文件工作区原型”，但还没有解决真实磁盘工作区、项目导入导出、增量构建和工程配置问题。下一步应优先接入 Storage Access Framework，并把项目模型从 `localStorage` 迁移为可导出的项目目录格式。

## 1.2 阶段进展：真实目录工作区

已在 `local-runtime` 分支接入 Android Storage Access Framework：

- “打开项目”使用 `ACTION_OPEN_DOCUMENT_TREE`；
- 持久化目录 URI 权限，应用重启后仍可访问；
- 递归读取 C/C++ 源文件和头文件；
- 限制单个项目文件为 2 MiB；
- 路径仅允许安全的相对路径；
- “保存项目”把当前文件写回选定目录；
- 不需要申请传统外部存储权限；
- 无 SAF 环境时继续使用 localStorage 草稿。

当前实现是第一版真实目录闭环：项目根目录使用 `.doge-project.json` 记录格式、项目名和 IDE 管理的文件。打开时优先按清单恢复，旧目录没有清单时继续递归扫描。保存时会创建或更新文件，并删除上一份清单中已从 IDE 项目列表移除的文件；项目目录中未被清单管理的文件不会被删除。仍未接入增量构建、文件变更监听或 Build Profile。

## 快速问题扫描

2026-09-27 使用快速 DeepSeek 探索代理对当前项目进行了只读扫描。以下问题仍需后续处理，按优先级排列：

### 高优先级

- Native runner 先写入 stdin 管道、后启动 WASI 执行；大输入可能阻塞，连续触发会占满 HTTP worker。
- Native runner 使用固定大小 JSON 缓冲区；较大的 stdout/stderr 可能截断 JSON，导致客户端只能收到无信息的 runtime_error。
- 项目文件删除没有确认、回收站或撤销；当前保存同步会删除上一份清单中已移除的文件。
- 已存在项目清单时只按清单加载，外部新增的 C/C++ 文件不会自动出现在项目中。

### 中优先级

- 清单损坏时打开和保存流程都可能失败，需要扫描降级或清单恢复机制。
- Debug 入口隐藏且没有有效快捷键，本地 Android 版本的调试代码不可达。
- release 构建仍可能回退到 debug 签名，targetSdk 仍为 28，正式发布配置尚未完成。
- 前端取消请求不会可靠取消 Android 服务端正在进行的编译或运行任务。
- WAMR native 执行入口没有显式串行化，多个 HTTP worker 并发执行存在运行时稳定性风险。
- 资源包导入缺少解压总量、条目数量和剩余空间限制。
- Activity 销毁后异步导入/打开回调仍可能访问已释放的 WebView。

### 低优先级和维护问题

- 编辑器每次击键都会保存完整项目并重绘文件列表，大项目下可能造成卡顿。
- Ctrl+S 当前没有完整接入真实项目目录保存语义。
- 本地执行结果中的部分 info 字段仍沿用旧云端响应字段。
- Android README、Manifest 注释和部分历史版本信息仍需继续与 local-runtime 实现对齐。
- 当前仓库存在未跟踪的 `report/新建 文本文档.txt`，未纳入版本提交。

本次扫描未修改代码。当前 C/C++ 切换 bug 已另行修复，并通过前端语法检查、Android Gradle 构建和 `git diff --check`。

## 后续问题修复进展

本轮已完成并通过 Android `assembleDebug`：

- C/C++ 文件切换时同步当前文件、语言模式和运行入口；
- 每次本地编译使用独立工作目录，避免并发请求互相覆盖；
- WAMR JNI 运行入口串行化；
- stdin 改为独立写入线程，避免大输入填满管道后阻塞执行线程；
- stdout/stderr 限制为 1 MiB，持续排空管道，并在 JSON 中返回截断标记；
- native 运行结果改用动态 JSON 缓冲区，避免固定 4 KiB 缓冲截断成非法 JSON；
- 项目清单损坏时降级为目录扫描；
- 已存在清单时合并目录中新发现的 C/C++ 源文件和头文件；
- 清单损坏时不执行旧文件删除，保存后重建清单，避免数据误删和保存死循环；
- README 和云端历史注释已按本地运行实现更新。

仍需后续处理：输入/输出压力测试、删除文件回收站或撤销、增量构建、clangd、真实调试、交互式终端和依赖管理。

- 项目文件删除增加应用内确认对话框；
- 编辑器输入使用防抖持久化，避免每个按键重绘项目列表；

- 本地运行信息不再依赖云端专有字段；
- 增加 `/api/v1/execution/cancel` 取消接口；
- native active WASM instance、watchdog 和 cancel 使用 mutex/generation 协调；
- 前端 Run 按钮在运行中触发取消请求；

## 卡死修复与资源导入进度

针对实机反馈的“应用彻底卡死”，本轮修复了 native 终止路径：`wasm_runtime_terminate()` 不再在 active mutex 内调用，避免 WAMR 终止过程与执行线程清理互相等待；执行线程会在撤销 active instance 后等待正在进行的终止调用结束，再执行实例销毁。资源导入新增解压进度回调和遮罩式进度条，显示读取、解压和完成状态。

本轮构建验证通过：Gradle `assembleDebug`、前端 `node --check`、`git diff --check`。当前环境未提供可调用的 `adb`，因此尚未重新安装到平板执行真实卡死回归；安装后应优先验证普通运行、超时、点击取消、返回退出 Activity，以及资源包导入进度显示。
